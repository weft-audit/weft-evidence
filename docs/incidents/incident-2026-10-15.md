# Postmortem: a 42-minute cascading failure in my multi-agent system

**Date:** 2026-10-15 · **Impact window:** 08:52:51–09:35:49 (local, UTC+8) · **Status:** closed with three fixes queued

This is a postmortem of a real outage in a small, self-built multi-agent system. Every time below comes from machine logs, not from memory. I claim part of the blame and record part of it with the provider.

## TL;DR

I ran a batch job that called a model API 30 times in sequence. The API had an intermittent overload that morning. My code had no error handling for abnormal responses, so the process crashed after ~17 minutes. Three consumers on the same provider channel went down one after another. The only component that survived was the one on a different provider.

## What went down

Three consumers shared one model provider that morning:

1. a worker agent — crashed after exhausting its max iteration count;
2. my chat engine — crashed, was restarted, crashed again;
3. the coding-agent session I was working in — its stream to the model kept dropping, so it stopped producing output.

One component stayed up the entire time: the auditor agent, which runs on a *different* provider. Its survival is the single most useful data point in this document.

## How I investigated

Three evidence chains, all from raw logs:

1. **Session logs.** They recorded every step of the batch job: when the command started, when items 1–11 finished, when item 12 hung, and the full stack trace when the process crashed. The crash pointed at a line with no error handling — it assumed a field in the API response always exists, like opening a drawer and assuming it is never empty.
2. **App log database.** Two raw lines, `SSE Error: Transport error: network error: error decoding response body`, plus ~27 minutes of auto-retry warnings. That explained the "reconnecting" message: the stream between the desktop app and the model service was breaking, not my own program.
3. **Live reproduction.** The next day, the same account and endpoint returned `503` with the body: *"Service is too busy. We advise users to temporarily switch to alternative LLM API service providers."* Minutes later, three consecutive requests all returned `200`. Balance was normal. Conclusion: intermittent provider overload, not billing.

## Root cause

Two layers, and I own one of them:

**External:** the provider had an intermittent overload that morning. I cannot control that, but the incident taught me the real lesson: I had put my whole household on one channel, and when that channel clogged, everything stopped.

**Mine, in three parts:**

1. I ran a newly written feature against real data for the first time, on a 30-item batch, with no small-scale trial first. The feature had only ever been tested in mock mode. This was the single worst decision of the day.
2. Every model call in my code assumed a well-formed response. A non-standard response (such as "we are busy") crashed the process instead of being logged, skipped, or retried. This was not a subtle bug; it was an absent design.
3. Nothing timed out for 15 minutes. The timeout covered connecting, not reading the response body, which could wait forever. I had no "give up after N seconds" and no "skip this item and continue", and the job left a half-finished state behind (11 of 30).

The weather was bad, and my car had no seatbelt.

## What I am changing

Only three fixes, all small:

1. Every API call logs abnormal responses and classifies failures; non-standard responses never crash the process.
2. Batch jobs get a dry-run mode; real-data runs start with a small trial batch.
3. A circuit breaker: a single call that exceeds its limit is abandoned, and consecutive failures stop the whole job with a report.

## Was verification my infrastructure?

In the first draft of this document I wrote that auditing and verification are my infrastructure. Then I asked myself what infrastructure actually requires: (1) other parts of the system depend on it by default; (2) when it breaks, the system cannot pretend nothing happened; (3) it is maintained and observable.

Measured against that, my verification layer currently scores two out of three: it is independent and it leaves records, but it is still triggered manually and has no monitoring. So it is not yet built infrastructure. It is what I am building, and this document is the first brick.

## What I could not verify

The exact response body of the 09:09 failure was never recorded by my program. My conclusion — the same class of overload as the reproduced 503 — is inferred from three facts: same account, same endpoint, reproduced error body; the stream failures in the same window; and a healthy balance. Time cannot be rewound, so this remains explicitly marked as inference rather than proof.
